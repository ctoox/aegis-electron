# 玻璃渲染性能：从 4fps 到 60fps

> 2026-10-05。触发原因：用户反馈「玻璃渲染有点卡，关掉之后比较流畅，但主要还是想用玻璃特效」。
> 本文记录测量方法、归因过程、改法，以及今后**不许再犯**的那一条。

## 1. 结论先行

| 场景（设置页滚动 + hover 扫过条目） | 均值 | p95 | p99 | >33ms 的帧 |
|---|---|---|---|---|
| 改前：玻璃开 | **82.1ms**（≈12fps） | **250.1ms**（≈4fps） | 281ms | **19** |
| 改前：玻璃关 | 15.6ms | 15.7ms | 15.7ms | 0 |
| **改后：玻璃开** | **15.8ms** | **15.7ms** | 31.2ms | **0** |
| 改后：玻璃关 | 15.6ms | 15.7ms | 15.7ms | 0 |

**玻璃的额外开销从 +1592% 降到 +0%。** 滚动时不再有掉帧。

## 2. 为什么会这么慢

本机是 Windows 10（build 19045），`detectMaterial()` 落到 **`inapp`** 分支 ——
系统没有开放的窗口模糊 API，于是由前端「页内玻璃」：body 铺一张彩色渐变底图，
再给一堆面板挂 `backdrop-filter: blur(30px) saturate(180%)`。

问题是**这些模糊层背后只有那张不动的底图**。对一张静态渐变做高斯模糊，每帧算出来
的结果完全一样 —— 纯白烧；而 Chromium 在滚动时并不会替你缓存这个结果，是逐帧重算。
更糟的是 `.page` 既是滚动容器又带模糊：**每一次滚动都要把整个右半屏重新糊一遍**。

## 3. 怎么测的

`scripts/bench-render.mjs`（走 CDP，在同一进程里做 A/B）：

```bash
npm run bench:render -- --user-data-dir <演示库目录> --password <主密码> [--rounds 3]
npm run bench:render -- --user-data-dir <目录> --password <密码> --ablate   # 消融：找瓶颈
```

- 指标是 `requestAnimationFrame` 的**帧间隔**（不是脚本耗时）—— 直接反映合成/绘制跟不跟得上
- 交互固定：设置页从顶滚到底、再滚回顶，中间用真实鼠标事件划过条目（触发 hover 重绘）
- **on/off 交替测量**，把「跑久了变热 / 被别的进程抢 CPU」这类漂移抵消掉
- 窗口必须真可见：被遮挡时 Chromium 会节流渲染，两边同样被节流的话数字全是噪声

## 4. 消融：谁在吃性能

`--ablate` 逐个关掉某层的模糊（基线 p95 250.1ms）：

| 关掉哪层 | 均值 | p95 | p95 相比基线 |
|---|---|---|---|
| 基线（全留） | 82.1ms | 250.1ms | — |
| 只去 `.page` | 49.9ms | 109.5ms | −56% |
| 只去 `.sidebar` | 63.1ms | 187.6ms | −25% |
| 只去 `.titlebar` | 73.9ms | 218.9ms | −12% |
| 去 `.page + .sidebar + .titlebar` | 27.5ms | 46.9ms | −81% |
| **全部去掉** | **16.8ms** | **31.2ms** | **−88%** |

结论：这几层**每一个都在实打实地花钱**，而它们糊的东西是同一张静态底图。
所以不是「留哪层、砍哪层」的问题，而是**这些模糊本来就不该存在**。

## 5. 改法

### 5.1 静态面板一律不模糊

`src/renderer/src/styles.css`、`styles-pages.css` 里删掉了这些选择器上的 `backdrop-filter`：

```
.titlebar  .sidebar  .listbar  .detail  .page
.health-card  .search  .detail-card  .gate-card
```

半透明底色（`--g-*` 那套 RGBA）**原样保留** —— 那才是「玻璃感」的来源。

### 5.2 只给真正盖在内容上的浮层留模糊

`.cmd`（命令面板）、`.modal`（弹窗）背后是**会滚动的内容**，模糊出来才是
「毛玻璃盖在内容上」的观感；而且它们按需打开，代价不落在日常滚动上。

### 5.3 底图改成独立的固定图层

```css
:root[data-mat="inapp"][data-glass="on"] body { background: transparent; }
:root[data-mat="inapp"][data-glass="on"] body::before {
  content: ""; position: fixed; inset: 0; z-index: -1;
  background: var(--g-bg); pointer-events: none;
}
```

原来用的是 body 的 `background-attachment: fixed` —— 那会让这张渐变一直挂在 body 的
绘制阶段里参与合成。独立图层只栅格化一次，实测 p95 从 31.3ms 降到 **15.7ms**。

> 这一步和 5.1/5.2 是**两件独立的事**，`--ablate` 之外另做了一次归因：
> 同一会话里分别注入「固定图层 + 有模糊」和「body 底图 + 有模糊」，两组采样值**逐色相同**
> —— 证明换图层这件事对渲染结果零影响。

## 6. 外观有没有走样：逐像素比对

同一会话、同一界面状态、同一滚动位置，只切换「那几层模糊」，全窗口 1752×1190：

| | 平均通道差 | 最大通道差 | 差 >8 的像素 | 差 >16 的像素 |
|---|---|---|---|---|
| 整体 | 0.83%（2.13/255） | 26 | 11.4% | **0.48%** |
| 纯背景区（无文字/卡片） | 1.65%（4.22/255） | 17 | — | — |

差的是**色块边缘的柔化程度**：底图本来就是渐变，去掉模糊后色块稍微「清晰」一点。
没有位移、没有错位、没有背景丢失。

> 中途踩的坑：第一版比对脚本里两次截图其实落在**不同视图**（导航点击没生效），
> 得出的数字是「41.6% 的像素差 >8、最大 50」—— 完全是假象。
> **做像素比对必须保证两张图是同一状态，最好在同一会话里只切一个变量。**

## 7. 平台影响范围

`--g-blur` 在 `data-mat="vibrancy" | "acrylic" | "mica"` 时本来就被覆写成 `none`
（系统在窗口背后画模糊，页面不能再糊一遍）。所以**被删掉的那些 `backdrop-filter`
在 macOS / Win11 亚克力 / 云母上一直是空操作** —— 这次改动对它们**没有任何影响**。
真正的受益者是 Win10 / Linux(UOS/麒麟等)：这些平台走 `inapp` 页面内玻璃。

## 8. 今后的规则

> **不要给「背后是静态底图」的面板加 `backdrop-filter`。**
> 它买不到观感，只会按帧收费。要加，先回答：这块面板背后**会不会变**？
> 不会变 → 用半透明底色 + 预先把渐变做柔；会变（盖在滚动内容上）→ 才可以上模糊，
> 并且要确认它是**按需出现**的。

护栏已经进了 `scripts/shot-ui.mjs`（设置页那一段）：

1. 预置条件：`data-glass === "on"`（否则下面那条在关闭玻璃时恒真）
2. 打开玻璃时，**带 `backdrop-filter` 的元素数必须为 0**
3. 底图那块伪元素的 `position` 必须是 `fixed`

## 9. 还没做的

- 改后 p99 仍有 31.2ms（约 1% 的帧走两个 vsync），玻璃关是 15.7ms。
  量级已经无所谓，但如果以后要继续抠，下一步该查的是 `.toasts` 那类常驻图层。
- 这三个数字都来自**固定的一台机器**（Win10 + 集显/独显未知）。macOS 的
  `vibrancy` 与 Win11 的 `acrylic`/`mica` 走系统实现，没法在本机验证 ——
  需要在真机上各跑一次 `npm run bench:render`。

## 10. 没装显卡驱动时：SwiftShader 与「内容从左上角铺开」

> 2026-10-05 追加。用户报「切换页面时整体会缩到左上角再变大」。

**先说结论：那不是布局坏了，也不是动画坏了，是这台机器没有 GPU 加速。**

### 10.1 怎么发现的

浏览器级 CDP `SystemInfo.getInfo`：

```
gpu_compositing: disabled_software      rasterization: disabled_software
opengl: disabled_off                    2d_canvas / webgl: unavailable_software
glRenderer: ANGLE (Google, Vulkan 1.3.0 (SwiftShader Device (Subzero)), SwiftShader driver-5.0.0)
vendor=5140(0x1414 Microsoft) device=0x008C
```

`0x008C` 是 **Microsoft Basic Render Driver** —— 没有可用显卡驱动时的兜底设备。
后来确认本机是**联想开天 N80z G2e（信创整机）+ 兆芯 KaiXian KX-7000**，
显卡面板显示「Microsoft 基本显示适配器」，即**没装兆芯集显驱动**（不是虚拟机，
`Get-CimInstance Win32_VideoController` 一查就知道）。

**这不是 Chromium 把某张卡拉黑了**，是系统层面没有可用的 GPU —— 代码里改不了。

### 10.2 为什么表现成「从左上角铺开」

没有 GPU 时所有合成/栅格都在 CPU 上跑。切页面要重画列 2–3 整块区域，
CPU 一帧画不完，合成器会**先把已经画好的分块呈现出来**；而栅格顺序大致是从左往右、
从上往下 —— 于是肉眼看到的就是「整块内容先从左上角冒出来，再慢慢铺满变大」。
用户会把它理解成动画/布局坏了，其实它是**画得慢**。

### 10.3 实测代价（本机，玻璃开）

复现命令：`npm run bench:switch -- --user-data-dir <演示库> --password <主密码>`
（第一行就会打印硬件加速状态；`--override '<css>'` 可做单变量消融）

| 场景 | 首绘（设置页第一次打开） | 稳态中位 | 稳态最大 |
|---|---|---|---|
| 切页面（基线） | 250ms | 31ms | 47ms |
| 底图加 `will-change: transform` | 266ms | 31ms | 47ms |
| `--num-raster-threads=6` | 234ms | 31ms | 31ms |

- 首绘那 250ms 是**页面自己第一次布局+绘制+栅格**；稳态只有 31ms（= 1 个掉帧）。
- 底图提层、加栅格线程**都不动这两个数字** → 瓶颈是页面内容的绘制复杂度。
- 逐帧几何采样 40 帧完全一致、screencast 抓了 5 种触发（切页/玻璃开关/最大化还原/
  快速连切/切主题）共 30+ 帧**帧帧完整** → 这个现象**不在渲染进程的输出里**。

> **看数量级，别看小数点。** 这台机器本身就慢、又会被别的进程抢 CPU：
> 同一配置相邻两次跑，稳态中位能差一倍（31ms ↔ 62ms）。要比较两个方案，
> 必须在同一台机器、同一时段、一次只改一个变量，并且**交替测**。

### 10.4 我们做了什么

代码层没有可抠的了（玻璃现在和「关玻璃」同价：31ms 对 31ms）。做的是**把这件事说出来**：

- 主进程 `detectAcceleration()`：读 `app.getGPUFeatureStatus().gpu_compositing`，
  `enabled`/`enabled_on` 才算启用。**故意现算**而不是模块加载时算一次 ——
  GPU 进程那时可能还没起来，会探成 `unknown`。
- `app:info` 带上 `gpu: { accelerated, status }`。
- 设置页「🎨 外观」下：未启用时给一条 `.sec-hint.warn`（写明现象、原因、怎么修）；
  「ℹ 关于」表里加一行「渲染加速 = 已启用 / 未启用（disabled_software）」。
- 护栏进 `shot-ui.mjs`，**跟着探测结果走**而不是"必须有提示"：
  `hintShown === !accelerated`。有硬件加速的机器上这条提示不该出现。

> **信创机型普遍如此**（兆芯/飞腾等平台常缺集显驱动）—— 这正是本项目的目标平台之一，
> 所以这条提示不是给个别人的补丁，是这类机器上的常态。

### 10.5 排错时最容易走的弯路

- **别急着在 CSS 里找**。几何采样证明布局没变、screencast 证明渲染进程输出是干净的
  —— 在这两件事做完之前，所有关于"是不是某个 CSS 属性"的猜测都是浪费。
- `Page.screencast` 的 `maxWidth/maxHeight` 是**等比缩放到框内**，不是上限。
  把 1325×900 当成"设备像素比 1.32"是误读，源就是 1001×680、DSF=1。
- screencast 用 PNG 编码大尺寸会**丢帧**（换 JPEG 帧数一样，说明是真没有那些帧）。

### 10.6 后记：驱动装上之后（2026-10-05 当天）

上面的现场证据是「**没装驱动**」时的状态，现在这台机器已经装上了（所以它仍然是
一条有效的**复现基线**，而不是错误结论）。装机后的实测：

```
硬件加速: 已启用 (gpu_compositing=enabled,
  ANGLE (0x00001D17, ZX C-1190 (0x00003A05) Direct3D11 vs_5_0 ps_5_0, D3D11-30.0.23.18))
```

- 显示适配器从「Microsoft 基本显示适配器」变为 **ZX C-1190**（兆芯集显），
  驱动 `30.0.23.18` / 2025-09-22。Chromium 走 **ANGLE → Direct3D 11**。
- **`shot:ui` 的那条提示自己消失了** —— `accelerated=true → 提示=false`、
  「关于」表显示「已启用」。至此那条护栏的**两个分支都验过了**：
  没驱动 → 出现；有驱动 → 不出现。（它当初的设计意图就是"跟着探测结果走"，
  这样有 GPU 的机器上不会出现一条查不出原因的警告。）
- **滚动**：p95 16.9ms / 0 掉帧（vsync 地板 16.67ms），玻璃额外开销仍是 **+0%** ——
  和软件渲染下的 15.7ms 没有实质差别，因为第 5 节的玻璃优化早就把这块压到 vsync 了。
- **切页**：整轮最大帧 **50ms**（软件渲染时是 218~438ms）。
- **但有一件事 GPU 帮不上**：切到设置页的**稳态**代价仍是 **33~35ms 一帧**，
  而主线程拆解显示那几乎全是**布局 35ms**（663 个布局对象 × 0.05ms/对象）。
  布局在 CPU 上、不受 GPU 影响 —— 想再往下走只能减少设置页的 DOM/布局规模，
  或者让它不要每次重新挂载。第 11 节的「首次」那一档同理（冷排版也是 CPU 侧）。

> 结论：**GPU 解决的是"栅格/合成"那一半；只要还有 663 个布局对象的整页重排，
> 切页就仍会有 ~1 帧的抖动。** 这两件事互不替代，别指望装驱动把布局也一起治好。

## 11. 首次打开设置页要 340ms：冷排版，与「后台预热」

第 10 节解释了**稳态**为什么慢（软件栅格）。这一节是另一半：**首次**打一个页面为什么
会比稳态贵 7~10 倍，以及怎么把这一下从用户眼前挪走。

### 11.1 现象

`bench:switch` 会把每次切换的主线程耗时拆成「脚本 / 样式 / 布局 / 任务」四列。
第一次打开设置页时，布局那一列直接爆表（玻璃开、软件渲染）：

```
切换              脚本ms   样式ms   布局ms   任务ms   布局次  样式次  节点增
[首绘]设置         33.5    12.2    337.2    422.9      2      3     663
[稳态]设置         21.0     8.3     33.9    116.1      2      9     663
[首绘]全部条目      10.5     8.7      6.1     81.3      1     15     100
```

- 脚本、样式重算、节点数都是一样的量级 —— **只有布局从 34ms 变成 337ms**。
- 用户看到的就是「点一下设置，整页卡住两三百毫秒」；软件渲染下还会叠上第 10 节的
  「内容从左上角铺开」。

### 11.2 三个桶不够用，得看事件级时间线

`Performance.getMetrics` 只能告诉你"布局很贵"，答不了"谁在布局"。上 `Tracing`
（`npm run trace:mount -- --user-data-dir <演示库> --password <密码> --target 设置`）：

```
ThreadControllerImpl::RunTask   306.1ms
 ↑ ProxyMain::BeginMainFrame    306.1ms     ← 合成器要一帧
   ↑ Document::UpdateStyleAndLayout 298.3ms
     ↑ LocalFrameView::layout   291.5ms     ← 一次全量布局
       beginData: dirtyObjects=369 totalObjects=482 partialLayout=false
```

**这一帧里没有脚本**（`long-animation-frame` 观察器也报"无脚本归因"）。同时栅格
（`RasterTask` 63 次合计 ~62ms）、样式重算（`Blink.Style.UpdateTime` 3 次 9.1ms）、
JS（`FunctionCall` 18 次 37ms）**全都不贵**。整个文档只有 482 个布局对象，这一次
排了其中 369 个 —— 合 **0.79ms/对象**，而正常水平是 0.005ms/对象。

> **读法**：`RunTask` 这个事件名其实叫 `ThreadControllerImpl::RunTask`，
> 而且**必须显式打开 `toplevel` 分类**才有。只开 `devtools.timeline` 会得到
> "RunTask 共 0 个" —— 那不是"没有长任务"，是"没抓到"。

### 11.3 关键对照：与页面无关，只与布局对象数相关

这正是把结论钉死的证据（同一台机器、同一时段）：

| 页面 | 首次挂载布局 | 布局对象 | 每对象 | 稳态每对象 |
|---|---|---|---|---|
| 全部条目 | 5.0ms | 100 | 0.05ms | — |
| 密码健康 | 71.5ms | 156 | 0.46ms | — |
| 设置 | 337ms | 663 | 0.51ms | **0.05ms** |

- 首次 **~0.45ms/对象**，稳态 **~0.05ms/对象** —— 差 9 倍，且**看不出与"哪一页"有关**，
  只随对象数线性放大。设置页只是对象最多，所以最惨。
- 「全部条目」首次只要 0.05ms/对象。**所以不是"进程里第一次布局都贵"** ——
  这条排除了"整体冷启动"的解释。

### 11.4 三个被证伪的假设（以及一个方法论错误）

| 假设 | 怎么验的 | 结果 |
|---|---|---|
| 全局字体/字形冷缓存（别人的页能替它预热） | `--visit "全部条目,设置"` 反向避让 | ✘ 反向仍 453.7ms ≈ 正向 431.6ms |
| 没做代码分割，首次挂载要解析新 chunk | 搜 `React.lazy` / `import()` | ✘ 全项目 0 处，只有一个 bundle；且 `ScriptDuration` 只有 33ms |
| 中文字体回退（DirectWrite 逐字找字体） | `--override '*{font-family:"Microsoft YaHei" !important}'` | ✘ 首布局 267.8 → 221.4ms，只降 17% |

> **★ 那条字体消融在原理上就是无效的。** 换字族 = 换一套冷缓存，它当然还是慢。
> 这类"用另一份同样冷的东西去替换"的消融，**注定测不出东西来**。
> 验证它需要的是"用同一份、先热再用"——也就是下面真正的改法。

### 11.5 改法：后台预热

缓存既然是**进程级**的（页面卸载不丢 —— 稳态挂载只要 34ms 本身就是证据），
那就可以在空闲时段先把它渲染一遍再拆掉。

`App.tsx` 里一条四态机（`idle → settings → health → done`）：

1. `gate === "ready"` 后等 600ms，再 `requestIdleCallback`（带 5s 超时兜底）；
2. 在 `.warm-layer` 里渲染设置页 → 停 700ms → 换成密码健康页 → 停 700ms → 拆掉；
3. 拆完在 `document.body.dataset.warmup = "done"` 留个记号（见护栏那节）。

**四个必须写进注释的约束**（每一条弄错都会**静默失效**）：

- **`visibility: hidden`，绝不能改成 `display: none`**。后者根本不建布局对象，
  预热等于没做 —— 而且界面看起来一切正常，只是第一次点设置又变回卡。
- **宽度要和真实内容区一致**（`.warm-layer { left: 210px; right: 0 }` 对着
  `.app { grid-template-columns: 210px 300px 1fr }` + `.page { grid-column: 2/-1 }`）。
  行盒宽度不同 → 断行不同 → 预热出来的是**另一批文本 run**，等于白热。
  改侧栏宽度时这里要一起改。
- **用户一点走就立刻收摊**（`view !== "vault"` → `done`）。否则他点「设置」的那一帧
  预热层还挂在 DOM 里，要多算 157 个节点 + 一次布局 —— 实测这一条就吃掉 40ms。
- **预热层绝不能留在 DOM 里**：`shot-ui.mjs` 里有 `querySelectorAll("*")` 的模糊探针
  和一堆 `p.sec-hint` / `.about-grid` 的 `.find()`，多一份隐藏副本会让它们
  **"照样找到元素，只是找到的是假的"**。

### 11.6 实测（A-B-A-B，同机同时段）

这台机器跨轮噪声大（见 10.3 的警告），所以做了两组互换对照：

| | 首次挂载布局 | 首次最贵一帧 | 稳态布局 |
|---|---|---|---|
| A1 无预热 | 337.2ms | 266ms | 33.9 / 37.0 / 36.6ms |
| A2 无预热 | 339.8ms | 250ms | 30.0 / 44.6ms |
| B1 有预热 | 89.1ms | 83ms | ~~55.8 / 54.7 / 56.2ms~~ |
| B2 有预热 | 83.8ms | 83ms | 34.5 / 36.6ms |
| **B3 有预热 + 离页收摊** | **49.7ms** | **83ms** | **35.3 / 36.3ms** |

- 首次布局 **337ms → 50ms（-85%）**；首次最贵一帧 **266ms → 83ms（-68%）**。
- **稳态无回归**（B1 那组 55ms 是噪声：同配置的 A 段两次都在 30~45ms，
  而记忆里这台机器"同配置相邻两跑能差一倍 31↔62ms"）。
- 剩下那 83ms 一帧里，布局只占 50ms，另 30ms 是栅格/合成 —— 那是第 10 节的
  显卡驱动问题，不是这一节能解决的。

### 11.7 排错时最容易走的弯路

- **`RunTask` 要带 `toplevel` 分类**，否则你看到的"0 个长任务"是假的。
- **`long-animation-frame`（LoAF）的 `renderStart` / `styleAndLayoutStart` 是绝对
  时间戳**（相对 `timeOrigin`），不是"相对帧起点"。忘了减 `startTime` 会打印出
  「帧 247ms = 渲染前 5081ms」这种自相矛盾的数。
- **`LayoutCount` 相同不等于工作量相同**：首次和稳态都是 2 次布局，耗时差 9 倍。
  只看次数会得出"没有布局抖动所以没问题"的错误结论。
- **`Layout` 事件的 `beginData` 是免费的**（`dirtyObjects` / `totalObjects` /
  `partialLayout`），一眼就能区分"只排了新挂的那棵"和"整篇文档重排"。
- **别用"换一份同样冷的东西"做消融**（见 11.4 的字体那条）。

## 12. 切页时「整体缩到左上角」：把三种可能逐个证伪之后

> 2026-10-05 追加。用户在装完显卡驱动后仍然报这个现象，并且直接质疑了第 10 节的归因：
> 「GPU 开了怎么还是有切换界面的时候缩小到左上角的问题，难道 CPU 的渲染逻辑和 GPU 的不一样？
> 所以还得再写一套 GPU 的？」

先把话放在前面：**第 10 节那句"装了驱动就好了"是不完整的**——驱动只把栅格/合成的
**单价**降下来了（218~438ms → 50ms 一帧），它不改变"整块内容换掉要重画一遍"这件事本身。

### 12.1 这句话出现过三个版本，含义一次比一次窄

| 用户说法 | 我们当时理解的 | 现在能确认的 |
|---|---|---|
| 「切换的过程中会有些整体变形，缩到左上角再变大」 | 不确定是切页还是切窗口 | —— |
| 「你说的『切换』具体是哪种？→ **切页面**」 | 换 `.page` 里的内容 | 下面 12.2~12.5 全部按这个口径查 |
| 「**GPU 开了怎么还有**」 | 说明第 10 节的归因不完整 | 确认：与 GPU/CPU 无关（见 12.7） |

### 12.2 代码层：没有任何会「缩小」的动作

把渲染层与主进程一起搜了一遍：

- 渲染层 CSS：`transform` 只出现 `translateY(±4px)`（`sel-in` / `fadeIn` 的入场位移）
  和 `translateX(18px)`（开关滑块）。**没有 `scale()`、没有 `zoom`。**
- 两个 `@keyframes` 只有 `sel-in 0.16s` 与 `fadeIn 0.22s`，都挂在**首次挂载**的元素上。
  反证很硬：还原态窗口下 40 次切页，屏幕上的变化**全部是单帧**（见 12.5），
  说明这两个动画压根没参与切页。
- 主进程：`setBounds` 只出现在 Auto-Type 面板（`autotype.ts`）；
  `maximize/unmaximize` 只挂在单次动作上（`index.ts:608`），与切页无关；
  没有 `zoomFactor`、没有 `--force-device-scale-factor`。
- 窗口构造：`frame: false`（Windows 全自绘标题栏）、本机 `MATERIAL = "inapp"`
  （Win10 19045 不做系统原生材质）、不透明底色、`minWidth 800 / minHeight 560`。

**结论：切页面在代码层没有任何"缩小"的动作可做。** 现象只可能来自
窗口呈现层或合成器。

### 12.3 窗口层：矩形全程恒定

用 `GetWindowRect` **每一帧都重新查一次**（不是只在开头查一次），三次运行都是恒定：

| 运行 | 窗口矩形（物理像素） | 1 小像素 = | 全程变化 |
|---|---|---|---|
| 还原态 | `(280, 120, 2000, 1360)` | 8 物理 px = 4 CSS px | 无 |
| 最大化 | `(-13, -13, 2586, 1626)` | 同上 | 无 |

本机是 **2560×1600 @200% 缩放**，所以 `dpr = 2`：1000×680 CSS 要 2000×1360 物理像素。
最大化的 `-13, -13` 与 +26 是 Windows 给"带边框最大化"留的拖边/阴影区，
**不是**窗口在动。

> 这一条把"窗口自己缩了"（`setBounds` / DWM 缩放交互 / 换显示器）整类假设排除了。

### 12.4 渲染进程层：几何恒定

`Page.startScreencast` + 逐 rAF 采样 `.page / .listbar / .detail` 的 `getBoundingClientRect`，
一次切页共 220 帧、按几何指纹分组 → **只有 2 个状态**（切换前 / 切换后），
`innerWidth/innerHeight` 全程 1000×680，没有任何中间态。

### 12.5 屏幕层：三条通道，只有一条"看见"东西

同一台机器、同一份演示库、同样的程序化切页，换三种抓法：

| 场景 | 抓取通道 | 帧间隔 | 切页次数 | 过渡段长（帧） | 多帧过渡 |
|---|---|---|---|---|---|
| 还原态 1000×680 | 屏幕 DC `BitBlt` | 67.5ms | 40 | **全部 = 1** | **0** |
| 最大化 1293×813 | 屏幕 DC `BitBlt` | 104.6ms | 30 | 1 / **4** / **6** | **3**（最长 780ms） |
| 最大化 1293×813 | **`PrintWindow`(PW_RENDERFULLCONTENT)** | **17.6ms** | 30 | **全部 = 1** | **0** |

"过渡段长"= 连续多少帧彼此都不相同（相邻帧差 > 3）。1 帧 = 原子切换。

另外两个由同一批帧得到的**硬事实**：

- **静止期相邻帧差恒为 0.00**，跳变**只有**和点击一一对应的那些
  （还原态 40 次点击 → 40 个跳变；最大化 30 次 → 30 个）。没有莫名其妙的抖动。
- 把最大化那 3 段多帧过渡按 **8×8 分块**判"这更像旧页还是更像新页"，得到的图案是
  **左两列 / 顶行 / 右列 / 底行先变成新页，中间一块矩形最后变**
  —— 即"一部分区域先更新、另一部分还是旧的"，不是平移、不是缩放、也不是均匀交叉淡入
  （这三种都测过：最佳平移只把残差从 17.43 降到 16.22；缩放扫描在 s=1.0 最优且往下单调变差；
  全局线性混合残差 16.99，几乎没改善）。

### 12.6 这个结果能推出什么、不能推出什么

**能推出：**

- 窗口没动、渲染进程输出没动。**现象不在 app 的布局/绘制代码里。**
- 那条"半更新画面"**只在屏幕 DC `BitBlt` 这条通道上出现**，而且只在最大化窗口下、
  约 10% 的切页上。
- **`BitBlt` 读 GPU 合成的最大化窗口本来就是不可靠的**：这类窗口经常走
  独立翻转 / MPO 覆盖层，像素不经过 DWM 合成缓冲，GDI 从屏幕 DC 去读会拿到
  过期的、或"正在被写"的内容。而"一部分区域已更新、另一部分还是旧的"正是这种读法的
  典型特征（不是撕裂线，是**矩形块**）。
- 采样率提高 6 倍、换成走窗口内容的 `PrintWindow` 之后，**中间态全部消失**。

**不能推出（必须说清楚）：**

- **不能断定"屏幕上真的没出现过那几帧"。** `PrintWindow` 会要求应用把窗口完整重画一遍，
  它在原理上**看不到**"屏幕上短暂显示了半更新画面"这种事 —— 它的干净不能当作反证。
- 反过来也不能因为 `BitBlt` 读到半更新就认定用户看到了：那可能只是读取端的不一致。
- 唯一能确定的否证是：**静止期恒定为 0 的帧差说明这条通道并非随机不可靠**，
  它只在重绘期间读到不一致 —— 也就是说，那个表面**确实在被逐块改写**。

> **一句话**：现象落在"窗口呈现/合成"这一段，而这一段目前我们手里**没有可信的观测手段**。
> 现有的两条一致快照通道（CDP screencast、PrintWindow）都说干净；
> 唯一说不干净的那条通道，恰好是公认对 GPU 合成窗口不可靠的那条。

### 12.7 需不需要给 GPU 再写一套渲染逻辑？——不需要，而且做不到

**Chromium 只有一条渲染管线。** GPU 与 CPU 的区别只发生在管线最末两段：

```
JS → 样式 → 布局(CPU) → 绘制/显示列表(CPU) → 分层 → 栅格 → 合成 → 提交给 OS → DWM
                                              ↑        ↑
                                        CPU: Skia CPU    CPU: GDI/软件呈现
                                        GPU: Skia Ganesh GPU: ANGLE→D3D11 / DirectComposition
```

**证据就在这台机器上**：装上驱动前后，`glRenderer` 从
`ANGLE (Google, Vulkan 1.3.0 (SwiftShader Device (Subzero)), SwiftShader driver-5.0.0)`
变成 `ANGLE (0x00001D17, ZX C-1190, Direct3D11 vs_5_0 ps_5_0, D3D11-30.0.23.18)`，
**应用代码一行没改** —— 同一份代码在两套后端上跑，这就是"同一个管线、两个后端"的直接证据。

而切到设置页的**稳态布局仍然是 33~35ms、与加速与否无关**（第 10.6 节），
这条也说明布局这一段根本不在 GPU 能管到的范围里。

所以"再写一套 GPU 的"等于重写整个 Chromium 的布局/绘制/合成 ——
**不是工作量问题，是没有第二个实现可选。**

### 12.8 下一步：三个方向，按性价比排

1. **让用户给出复现条件。** 本机还原态 40/40 干净、最大化下两条一致通道也干净，
   所以必须拿到"什么窗口大小 / 哪两页之间 / 能不能稳定复现"。
   （用户的"有些"提示它不是每次都发生 —— 最大化那 3 次多帧过渡是 30 次里的 3 次，
   概率量级吻合。）
2. **加 A/B 对照，把"直配/独立翻转路径"单独关掉看现象是否消失**：
   `--disable-direct-composition` / `--disable-gpu-compositing` / `--disable-gpu`。
   这是唯一能把"合成器呈现路径"单独拎出来的实验。
3. **工程性缓解（在以上任何假设下都是唯一有效的杠杆）：把每次切页的整窗重绘面积降下来。**
   现在切页会把整棵页面树卸载再挂载，等于对整块内容区做一次全新栅格。
   如果让两页常驻、只切 `visibility`，栅格结果就可能被复用，
   而不是每次都重画一遍。**这一条不依赖现象的真因，值得先做。**

### 12.9 这一节的两个通用教训

- **★ 断言"某个坏结果没发生"的探针，必须先证明"观测手段能看到它"。**
  这里差点犯两次：先是用 6.4fps 的采样去否定 1 帧（16.7ms）的瞬态（漏掉概率 16%），
  后用 `PrintWindow` 的干净去否定"屏幕上出现过半更新"（原理上看不到）。
  **每一次都要问：我要防的这个东西，我这套观测在原理上有没有可能看到？**
- **★ 屏幕级抓取要选对通道。** 对 GPU 合成的最大化窗口，GDI 屏幕 DC `BitBlt`
  会读到半更新的矩形块，而这些块**不代表屏幕上出现过什么**。
  要做"屏幕级"判定，必须同时用一条不经过扫描输出的通道（`PrintWindow`）交叉验证；
  两条通道不一致时，先怀疑抓取，再怀疑应用。

## 13. 「给内容区加 `contain` 限伤」：消融做了，**没有可测收益**

> 2026-10-05 追加。第 12 节把现象推到了"重画代价"这一层，于是试最省事的一招：
> 给内容容器加 `contain: layout paint`，让换页的过程只脏容器内部。

### 13.1 怎么做的

不改源码 —— `bench:switch` 本来就有 `--override`，正好做单变量消融：

```bash
npm run bench:switch -- --user-data-dir <演示库> --password <密码> --rounds 8 \
  --override '.page,.listbar,.detail{contain:layout paint}'
```

A-B-A-B 交替四轮（同机、同时段、一次只改一个变量）：`A1 → B1 → A2 → B2`。

**先证明注入生效**（否则"数字没变"会被误读成"这个属性没用"）：

```
PASS  注入元素=true  生效选择器=3/3
  .page     匹配 1   contain = layout paint
  .listbar  匹配 1   contain = layout paint
  .detail   匹配 1   contain = layout paint
```

### 13.2 结果：全部落在噪声里

| 指标 | A1 | B1（contain） | A2 | B2（contain） |
|---|---|---|---|---|
| 稳态·设置 布局 ms | 34.2 | 30.4 | 29.6 | 35.7 |
| 稳态·设置 任务 ms | 110.3 | 98.0 | 96.6 | 112.7 |
| 稳态·设置 布局次 | 2 | 2 | 2 | 2 |
| 稳态·设置 节点增 | 663 | 663 | 663 | 663 |
| 稳态·全部条目 布局 ms | 6.5 | 5.1 | 5.6 | 4.5 |
| 帧中位 / p95 | 17/17 | 17/17 | 17/17 | 17/18 |
| 最贵帧·首绘·设置 | 117 | 67 | 83 | 67 |

- **A 段自己两跑就差 34.2 → 29.6（−13%）**，而 B 全落在 A 的区间内
  → 效果**低于本机噪声地板**（本机同配置相邻两跑能差一倍，见第 10.3 节）。
- `布局次` 和 `节点增` **四轮完全一致**：既没少排一次布局，也没少建/少拆节点。

### 13.3 为什么注定没用（想清楚之后就不用再试了）

**`contain` 防的是"容器里的改动外溢"，而换页是"整个容器被换掉"。**

- 换页时被作废的是列 2–3 那一片内容区：旧的两个 grid item 被移除、新的 `.page` 被加入。
  **要重画的范围不因容器有没有 containment 而改变** —— 换的本来就是整个容器。
- `contain: layout` 只是不让容器内的改动影响**外部**布局；新挂的那棵树该排还得排，
  663 个对象 × 0.05ms ≈ 34ms（正好对上表里的布局列）。
- `contain: paint` 同理：新内容该画还得画，containment 不会让新内容变小。

它真正有用的地方是**页内改动**（在搜索框里打字、切换某一行的开关）—— 那时
改动只脏一行，containment 能挡住祖先链被连带失效。那是另一个场景、另一笔账，
而且那时的脏区本来就只有一小块。**所以这一条没有落地，不值得为它承担
`.listbar` 本来没有 `overflow` 却被 `paint` 裁掉的风险。**

### 13.4 这一轮真正留下的东西：消融工具会自己说"我有没有生效"

这次是**先跑了验证器才知道注入生效**的，反过来就危险了。所以把这个守卫
直接做进了工具：`bench:switch` 注入 `--override` 之后会打印**每个选择器的命中数**，
一个都没命中就直接说"本次消融无效"。

```
已注入 --override: .page,.listbar,.detail{contain:layout paint}
  override 命中: .page=0   .listbar=1   .detail=1
```

（`.page=0` 不是失败 —— 注入时停在"全部条目"，设置页容器本来就不在场。
所以判据是"**全部为 0** 才无效"，而不是"有一个 0 就失败"。）

### 13.5 那还剩哪条路

表里的账很直白：**稳态·设置 每次切换 ≈ 100ms 主线程，其中布局 34ms 是最大的单项，
而它全部来自"新挂的那棵树要重新排一遍"。** 想动它只有一条路：

**别整棵重挂**（keep-alive：两页常驻、只切 `visibility`，或 `display`）。
理由不只是"省一点"，而是 —— 常驻之后那棵树**没有被弄脏**，
`visibility` 切换不需要重新布局（§11 已经量过：首次 0.45ms/对象、稳态 0.05ms/对象，
两者差的正是"这棵树是不是新造的"）。

**但代价要先算清楚**：隐藏副本会让 `shot-ui.mjs` 里所有"按文字找元素"的探针
**照样找到元素、只是找到的是隐藏页里那个** —— 这跟 `.warm-layer` 那条教训
（第 11 节：预热层绝不能留在 DOM）是同一个形状，必须先给它上 `inert` +
`aria-hidden` 并把探针门槛收紧，否则是拿一组静默变绿的探针换几个毫秒。

> **一句话**：`contain` 这条不用再试了。要省那 34ms 布局，只能改"页面是不是常驻"，
> 而那是要连测试护栏一起改的改动，不是加一行 CSS 的事。

## 14. 换到高刷屏（90Hz / 160Hz）要不要改？

> 2026-10-05 追加。背景：本机面板 `ZX C-1190` 的 `MaxRefreshRate=90`（当前跑 60Hz），
> 之后会换到 160Hz 的机器上。问题：**应用要不要为高刷做适配？**

### 14.1 结论先说

| 对象 | 要不要改 | 为什么 |
|---|---|---|
| **应用代码**（`src/`） | **不用改** | Chromium 的呈现节奏跟着显示器走，没有"60Hz 假设"可拆 |
| **测量工具的判据** | **要改**（本轮已改） | 它们把"多少 ms 算掉帧"写死成 60Hz 的值 |

应用侧不改，是有具体依据的，不是"应该没问题"：

- `src/` 里**没有**任何 `appendSwitch` / 强制 GPU / 强制帧率的命令行开关（`grep` 过）。
- 全仓唯一出现 `16.7` / `1000/60` / `vsync` 的地方是 **bench 脚本和本文档**，不是产品代码。
- CSS 的过渡与动画（`sel-in 0.16s`、`fadeIn 0.22s`）是**按时长**算的，与刷新率无关；
  高刷只会让同一段动效更平滑，不会变快或变慢。

### 14.2 为什么判据必须跟着刷新率走

**"多少 ms 算掉一帧"随刷新率变**：

| 刷新率 | 1 帧 | 掉 1 帧（≈2 vsync） | 掉 2 帧（≈3 vsync） |
|---|---|---|---|
| 60Hz | 16.7ms | 33.3ms | 50.0ms |
| 90Hz | 11.1ms | 22.2ms | 33.3ms |
| 160Hz | 6.3ms | 12.5ms | 18.8ms |

把 33ms 写死，换到 90Hz 上判据就**宽了一半**；160Hz 上宽了一倍多。
后果是**一个方向的失真**：掉了帧也报"没掉" →
"这台机器渲染没问题"这种结论会在换机后**静默**变成假话。

举个能一眼看懂的例子（也是测试里固化的那条）：
**一个 25ms 的帧，在 60Hz 下不算掉帧（33.3 门槛），在 90Hz 下算掉帧（22.2 门槛）。**
同一个数字，不同结论 —— 所以判据不能写死。

### 14.3 改了什么

新增 `scripts/lib/refresh.mjs`：

- `detectRefresh(cdp)` —— 让页面**空闲地**跑 ~45 帧 rAF，取**帧间隔中位数** → Hz。
  探不到（被遮挡节流）就退回 60Hz，并让调用方把"没探到"打印出来。
- `hzFromMedian(med)` —— 中位 → Hz 的**纯函数**（3~40ms ≈ 25~333Hz，超出判"不是刷新率"）。
  抽出来是为了**能对 60/90/160 三档直接断言**，而不是只能在真机上碰运气。
- `drop1Ms(vsyncMs)` / `drop2Ms(vsyncMs)` —— 2×/3× vsync。

`bench-render.mjs` / `bench-switch.mjs` 接入后，报告头多一行：

```
渲染节奏: 实测帧间隔中位 16.70ms → 约 60Hz；判据: 掉1帧 > 33.3ms，掉2帧 > 50.0ms
```

逐帧那一节也从硬编码的 `>33ms / >50ms / >100ms` 换成
`掉1帧 / 掉2帧 / 严重`（门槛都由实测 vsync 算出）。
**60Hz 下这些数字和以前完全一样**，所以旧日志仍可直接对比。

`tests/refresh.test.ts`（13 项）把三档映射与"同一帧不同判据"固化下来；已做**红测**：
把 `drop1Ms` 故意写死成 33.3 → 测试在"25ms 帧 @90Hz"那条变红、退出码 1 → 恢复后全绿。

### 14.4 它测的是"应用拿到的节奏"，不是显示器的标称值

这一点得说清楚：探测取的是 **rAF 实际出帧的中位间隔**。

- 若合成器把 rAF 压到 60Hz，这里就**报 60** —— 而判"有没有掉帧"本来就该拿
  实际呈现节奏当基准，所以这是**对的**，不是 bug。
- 反过来：**换到 160Hz 的机器后，如果这里报的还是 60，那就是个信号**，
  说明 rAF 被压住了（软件合成 / 窗口被遮挡 / 合成器限帧）——
  这时该查的是加速状态那一行，而不是怀疑面板。

**前提**：窗口必须真在前台。被遮挡时 Chromium 把 rAF 节流到 ~1Hz，
中位会大得离谱 → 按"探测失败"处理并显式标注，不会硬凑一个 Hz。

### 14.5 更硬的约束：高刷屏只有在"每帧画得完"时才有意义

探测判据解决了**怎么量**，但**能不能跑满**是另一件事：

- 本机实测 ~15.7ms/帧（§10.6，装驱动后 16.9ms / 0 掉帧，都贴着 vsync 地板）。
- 160Hz 的预算是 **6.25ms/帧**。本机这 15.7ms 的账**在本机上无论面板多快都跑不过 60fps** ——
  瓶颈是渲染成本，不是显示器。
- 换到 160Hz 的机器（CPU/GPU 更强），**同一套代码**自然会更便宜；
  但那个数**只能在那台机器上量**，本机测不出来。

所以"要不要为 GPU/高刷另写一套渲染逻辑"这个问题的答案是**否**（§12.7 同理）：
Chromium 只有一条管线，换机器换的是后端速度，不是代码路径。

### 14.6 未验证项（诚实标注）

- **90Hz / 160Hz 的真实路径，本机没跑过** —— 本机面板当前是 60Hz，
  切到 90Hz 要改显示设置，本轮没做。已验证的是：探测在 60Hz 上返回 60、
  以及"中位→Hz / 判据"的纯函数对三档都正确（已进测试）。
- 真正到 160Hz 机器上，第一件事就是在那边跑一次 `bench:switch`，
  先看报告头那行报的是不是 160 —— 报 60 就按 §14.4 去查加速状态。
